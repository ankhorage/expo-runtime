# AGENTS.md

## Scope

This file applies to the whole `ankhorage/expo-runtime` repository.

`@ankhorage/expo-runtime` is the Expo platform runtime package for Ankhorage.
It translates platform-neutral app requirements into Expo-specific runtime
planning and runtime wiring. Keep it reusable by generated apps, Studio preview
hosts, and other Expo consumers. Do not turn it into product logic, template
logic, or generic runtime core.

## Repository facts

- Package name: `@ankhorage/expo-runtime`.
- Runtime: Bun.
- Language: TypeScript, ESM, strict mode.
- Platform target: Expo / React Native / React Native Web.
- Main source root: `src/`.
- Build output: `dist/`.
- Public root export: `src/index.ts`.
- README is generated by Paradox. Do not edit `README.md` manually; update
  source/docs and regenerate where applicable.

## Core architectural rules

### Expo runtime owns Expo-specific resolution

This package owns Expo-specific mappings such as:

- permissions to Expo permission support metadata
- capabilities to implied permissions
- capabilities to required npm packages
- native app config/plugin planning
- runtime providers needed by Expo capabilities
- runtime adapters and component registry overrides

Good:

- `barcodeScanner` implies `camera`
- `camera` contributes Expo app config/plugin entries
- `BarcodeScannerView` maps to `ExpoBarcodeScannerAdapter`
- generated apps and Studio preview use the same Expo runtime registry

Avoid:

- generated app business logic
- Studio-only selection or overlay behavior
- product lookup or nutrition workflows
- route generation or template copy
- platform-neutral runtime ownership that belongs in `@ankh/runtime`

### Runtime core stays outside this package

`@ankh/runtime` is the generic manifest runtime. Keep this package focused on
Expo platform concerns layered on top of that runtime shape.

Do not move generic runtime concerns here:

- runtime action dispatch rules
- generic component rendering
- generic manifest binding resolution
- Studio authoring state

### ZORA stays adapter-neutral

ZORA components remain platform-neutral UI. This package may import ZORA
components and prop types when implementing Expo adapters, but it must not push
Expo-native APIs back down into ZORA.

Good:

- `ExpoBarcodeScannerAdapter` renders ZORA `BarcodeScannerView`
- native camera payloads are normalized before being forwarded

Avoid:

- editing ZORA metadata from this package
- putting Expo package names into ZORA requirements metadata
- product-specific labels or scanner flows in the adapter

### Declarative planning first

Capability, permission, package, and config resolution must stay declarative.
Prefer registry/metadata tables over scattered conditionals.

Good:

- capability metadata maps `barcodeScanner` to `expo-camera`
- provider/package/config hints are derived from a plan

Avoid:

- `if (permission === 'camera') add expo-camera` spread across callers
- hardcoded generator checks outside the plan resolver

### Studio parity matters

Studio is not a generated app, but when Studio previews a generated Expo app it
must use the same Expo runtime registry/config that the generated app uses.

This package should make that possible by exposing reusable runtime helpers that
can be shared by:

- generated app runtime layout code
- Studio preview hosts rendering generated app content

Do not add Studio-specific selection, panel, or admin behavior here.

## Public API rules

Public exports should stay intentional and small.

Expected public surface:

- Expo runtime plan types and resolver
- Expo runtime providers wrapper(s)
- Expo runtime adapters
- Expo component registry factory
- normalized helper utilities used by the adapters

When changing public behavior:

1. update `src/index.ts`
2. add or update tests
3. add a changeset
4. regenerate docs if README/API docs need to change

Do not rely on deep imports from consumers when a root export is appropriate.

## Testing rules

Cover both planning and runtime wiring.

Preferred coverage areas:

- permission and capability planning
- dependency/config plugin planning
- provider composition
- adapter payload normalization
- component registry overrides

Keep tests focused and platform-specific. Avoid broad integration fixtures when a
small declarative unit test proves the same contract.
